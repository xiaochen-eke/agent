# Dify 版饥荒物品顾问 · 配置指南

> 目标：在 Dify 里搭一个与 native / langgraph 版同源的「意图识别 → 条件分支 → 工具查库 → 汇总」工作流，
> 物品库仍跑在宿主机 `items_server`(:5099)，Dify 经 `host.docker.internal` 访问它。
>
> 三版本做的是同一件事，只是编排方式不同：
> - native：手写 `if/elif` + 直接 `import lookup()`
> - langgraph：`StateGraph` 节点 + `add_conditional_edges`
> - dify：可视化拖节点（LLM / Code / 条件分支 / HTTP 请求）

---

## 〇、与方案的差异（先说清楚，踩过的三个坑）

方案里 Dify 版画的是 5 节点 + 1 条件分支。但实际在 Dify 1.x 里要落地，必须做三处调整，最终是 **9 节点**：

1. **JSON 子字段没法直接被 if-else 判断** → 加一个 **Code「解析意图」** 节点，把 LLM 的 JSON 文本 `json.loads` 成 `intent` / `item` 两个变量。这正是 native 版 `detect_intent()` 里那行 `json.loads`、langgraph 版 `node_intent()` 里 parse 的 Dify 等价物。
   - 额外注意：**deepseek 这类推理模型会包一层 `<think>...</think>` 前缀**，直接 `json.loads` 会失败。Code 里要先 `find("{")` / `rfind("}")` 把最外层 JSON 抠出来再 parse（见 3.3 的代码）。
2. **HTTP 节点 query 参数格式**：Dify 1.x 的 `params` 是**每行 `key: value`（冒号分隔，换行分隔多个）**，不是 `key=value&...`。写错了参数不会传过去。
3. **条件分支两条线不能收敛到同一个下游节点**：下游节点引用「另一条线上没执行的节点」的输出变量时，运行会报 `Variable #xxx# not found`。所以 `recipe/stats` 和 `other` 两条线各配一个回答 LLM + 一个结束节点（与 native/langgraph 的「有信息→汇总 / 无信息→直接答」两条路径一一对应）。

最终结构：

```
开始 → 意图识别 → 解析意图 → 条件分支 ─┬─(recipe/stats)→ 查物品库 → 汇总回答 → 结束
                                       └─(other)→ 直接回答 → 结束
```

## 四、手搭版（导入失败时照此手搭，更可靠）

### 4.0 建应用

创建应用 → 选「工作流」→ 名称 `饥荒物品顾问`。

### 4.1 节点 0 · 开始

「开始」→「+ 添加输入字段」：文本 / 变量名 `query` / 字段名 `问题` / 必填。

### 4.2 节点 1 · LLM「意图识别」

- LLM 节点，标题 `意图识别`，模型 `glm-4-flash`（或 deepseek）。
- 系统提示词：
  ```
  你是《饥荒》物品顾问。判断用户问题属于哪类，并提取物品名。recipe=问某物品怎么合成/怎么做；stats=问属性/效果/数值；other=与物品无关。只输出 JSON，格式：{"intent": "recipe|stats|other", "item": "物品名(other 时空)"}
  ```
- 用户提示词：`{{#开始.query#}}`

### 4.3 节点 2 · Code「解析意图」

- Code 节点，标题 `解析意图`，语言 `python3`。
- 输入变量：变量名 `raw`，值选 `{{#意图识别.text#}}`。
- 代码（**先抠 JSON 再 parse，兼容 deepseek 的 think 前缀**）：
  ```python
  def main(raw: str) -> dict:
      import json
      obj = {}
      text = raw.strip()
      i = text.find("{")
      j = text.rfind("}")
      if i != -1 and j > i:
          text = text[i:j+1]
      try:
          obj = json.loads(text)
      except Exception:
          obj = {}
      return {"intent": obj.get("intent", "other"), "item": obj.get("item", "")}
  ```
- 输出变量：`intent`（string）、`item`（string）。

### 4.4 节点 3 · 条件分支

- 条件分支节点，标题 `条件分支`。
- 条件 1（IF）：`解析意图.intent` **是** `recipe`
- 条件 2（OR）：`解析意图.intent` **是** `stats`
- 逻辑关系：条件 1 **或** 条件 2（`or`）。
- ELSE 分支自动存在（`other` 走这里）。

### 4.5 节点 4 · HTTP「查物品库」（连到 IF/OR 的「是」出口）

- HTTP 请求节点，标题 `查物品库`，方法 **GET**。
- URL：`http://host.docker.internal:5099/lookup`
- 参数（**每行 `key: value`，冒号分隔**）：
  ```
  item: {{#解析意图.item#}}
  intent: {{#解析意图.intent#}}
  ```
- 该节点输出 `body`（**是字符串**，JSON 原文，直接引用 `body` 即可，别写 `.result`）。

### 4.6 节点 5 · LLM「汇总回答」（连到「查物品库」之后）

- LLM 节点，标题 `汇总回答`，模型同「意图识别」。
- 系统提示词：`你是《饥荒》物品顾问。根据【物品信息】用中文友好回答。`
- 用户提示词：
  ```
  问题：{{#开始.query#}}
  【物品信息】{{#查物品库.body#}}
  ```

### 4.7 节点 6 · LLM「直接回答」（连到条件分支的 ELSE 出口）

- LLM 节点，标题 `直接回答`，模型同「意图识别」。
- 系统提示词：`你是《饥荒》物品顾问。用户的问题与饥荒物品无关，请友好地说明你只回答饥荒物品相关的问题。`
- 用户提示词：`问题：{{#开始.query#}}`

### 4.8 节点 7 / 8 · 两个「结束」节点

- 「结束A」（连「汇总回答」之后）：输出变量 `answer` = `{{#汇总回答.text#}}`。
- 「结束B」（连「直接回答」之后）：输出变量 `answer` = `{{#直接回答.text#}}`。

> 两条分支各一个结束节点，不要收敛到同一个——否则另一条线没执行的节点变量会报 not found。

### 4.9 连线

```
开始 → 意图识别 → 解析意图 → 条件分支 ─┬─(是 recipe/stats)→ 查物品库 → 汇总回答 → 结束A
                                       └─(否 other)→ 直接回答 → 结束B
```

## 五、测试

1. 右上「运行」→ 输入 `query` = `草帽怎么合成？`
   - 意图识别输出 `{"intent":"recipe","item":"草帽"}`
   - 解析意图输出 `intent=recipe, item=草帽`
   - 条件分支走「是」→ 查物品库 `body` = `{"result":"草帽的合成配方：12×干草", ...}`
   - 汇总回答输出中文回答
2. 再测 `今天天气如何？` → 走 ELSE 分支，跳过查物品库，`直接回答` 输出「我是饥荒物品顾问…」。
3. 对照 native / langgraph 版，三版对同一输入应输出语义等价的回答。

## 六、面试可讲的点

- **平台 vs 手写**：同一功能，native 是手写控制流，langgraph 是代码建图，dify 是可视化拖节点——何时用哪个。
- **JSON 解析的差异**：native/langgraph 在 Python 里 `json.loads`，Dify 里要显式用 Code 节点——「框架替你做的 vs 平台要你显式做的」。
- **host.docker.internal**：Dify 跑在容器，`127.0.0.1` 是容器自身；访问宿主机服务必须用 `host.docker.internal`（容器网络隔离经典考点）。
- **工具调用是真实的 HTTP 调用**：不是把物品库塞进 prompt，而是「条件分支 → HTTP 查 :5099 → 结果喂给汇总」。
- **图执行 vs 代码执行的差异**：Dify 分支下游引用「未执行节点的变量」会报 `Variable not found`，而 Python/LangGraph 里默认值天然规避——可视化平台的状态管理约束。
- **推理模型的前缀**：deepseek 输出带 `<think>` 推理块，解析前要先抠 JSON——接不同模型要适配它的输出格式。
